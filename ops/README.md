# Эксплуатация «Т-Технологии 850»

Конвейер модели справедливой стоимости акции МКПАО «Т-Технологии» на общем сервере
панелей владельца: сбор источников, дозор релизов МСФО и решений о дивидендах,
нау-каст, сборка выпуска `t-v1`, публикация в публичный репозиторий данных, сверка
через боевую дверь `https://tzi-850-t.pages.dev/api/model`. Конвейер — копия
конвейера панели Сбера (схема «Ленты», каркас — панели Магнита 850oa); на сервере
это вторая панель банков, её такты сдвинуты от соседних (раздел 3). Что в копии
своё, а что общее — `docs/PORTING.md`.

Здесь — всё, что нужно для работы с конвейером, без инфраструктурных подробностей
сервера (адрес, имена ключей, доступы): они в справочнике владельца вне
репозитория. Репозиторий публичный, правило гигиены держит
`tests/test_public_hygiene.py`.

## 2. Канал данных

```
сборка (python -m model.build_release) → $BANK_STATE_DIR/release/latest.json
  → ops/publish.py: клон ветки release, releases/<sha256>.json + latest.json + history.json (+ journal.json) одним коммитом, push
  → GitHub Pages репозитория данных (сборка pages-build-deployment, обычно 1–3 минуты)
  → functions/api/model.js: Pages (минутная метка, cacheTtl 60) → raw (запасной) → копия края
  → браузер и сверка ops/publish.py --verify
```

- **Ветка только дописывается.** `releases/<sha256>.json` пишется один раз и не
  трогается никогда (прореживания нет); `latest.json` — указатель, `history.json` —
  строка на каждую публикацию и откат (PAYLOAD §4), `journal.json` — полный журнал
  прогнозов. Правило репозитория данных — без удаления ветки и без перезаписи
  истории; push — без силы.
- **Выпуски и журнал пишутся компактно** — без отступов, разделители `,` и `:`
  (выпуск на треть меньше, чем с отступами). **Сторож объёма:** после публикации
  `publish.py` меряет дерево ветки (файлы клона без `.git` — то, что раздаёт сайт
  GitHub Pages) и с порога `ops/budgets.json` → `data_branch_alert_mb` (700 МБ при
  пределе сайта 1 ГБ) отвечает кодом 3: выпуск на витрине, такт кончается
  «ТРЕВОГА (код 8)» со строкой «ПУБЛИКАЦИЯ: дерево ветки release — … МБ». Рост —
  раздел 9.
- **Хэш** `meta.payload_sha256` — по правилам PAYLOAD §0.4 (вне хэша: моменты
  сборки и публикации, ссылки на прошлые выпуски, размер, `live.fetched_at`, ссылки
  журнала на выпуски, блоки `changes` и `valuation_history`).
- **Повтор без дублей.** Выпуск с тем же хэшем, что уже в указателе, повторно не
  публикуется: ни коммита выпуска, ни строки истории (журнал обновится, если
  изменился); сверка получает `published_at` того, что уже в указателе. Быстрая
  сборка (`meta.fast: true`) не публикуется никогда.
- **`meta.published_at`** — момент публикации (UTC, ISO, секунды), вне хэша;
  вписывается при каждой публикации и откате. Из него дверь ставит
  `Last-Modified` (по нему живёт сторож) и сильный `ETag` `"<sha12>.<секунды>"`.
- **Коммит — только при разнице**; push — три попытки с растущей паузой, каждая с
  чистого клона; `gc.autoDetach=false` (systemd убил бы фоновый `git gc` и оставил
  `*.lock`). Автор коммитов — `TTECH_GIT_NAME`/`TTECH_GIT_EMAIL`, только
  noreply-адрес GitHub из `.github/commit-emails.allow` (сверяется со списком:
  чужой noreply и отсутствие списка — отказ, код 1).
- **Охрана каталога клона** — до любой разрушающей команды: каталог клона
  (`BANK_DATA_REPO_DIR`) не совпадает с каталогом состояния или кода и не лежит
  выше них; непустой каталог без `.git` не удаляется; каталог с `.git` обязан быть
  клоном данных этой панели — есть `refs/remotes/origin/release`, и origin
  указывает на тот же репозиторий, что `TTECH_RELEASE_REMOTE` (сменить можно
  ssh-алиас, но не репозиторий: клон данных соседней панели не трогается). Иначе —
  «ПУБЛИКАЦИЯ: каталог клона данных …» или «ПУБЛИКАЦИЯ: в каталоге … клон другого
  репозитория данных», код 1, и ни один файл не тронут: опечатка в переменной
  иначе стёрла бы журнал прогнозов и невосполнимый архив — молча и на каждом такте.
- **Git без хуков:** каждая команда git публикации идёт с
  `core.hooksPath=/dev/null` и `core.fsmonitor=false` — хук или монитор файлов из
  клона данных не исполнится в такте, у которого есть ключ записи. Это наименьшие
  права, а не граница доверия: `.git/config` клона пишет тот же пользователь.
- **Сверка** читает дверь, как браузер (свой ASCII User-Agent: без него дверь
  отвечает 403), до совпадения `payload_sha256` И `published_at`. Окно —
  `TTECH_VERIFY_TIMEOUT` (600 с), пауза — `TTECH_VERIFY_PAUSE` (30 с). Итоги:
  - совпало, `x-data-source: pages` — строка журнала «СВЕРКА: выпуск <sha12> ·
    <момент> — пройдена с попытки N, Last-Modified …», `release.commit` = коммит
    кода выпуска, отметка `release.pushed` снимается, код 0. По этой строке и по
    `release.commit` принимают установку и каждый выпуск (раздел 5, шаг 12);
  - совпало через `raw` или `edge-cache` — выпуск засчитан, но GitHub Pages не отдаёт ветку: код 3 (тревога);
  - не дождались — код 3, `release.pushed` остаётся, `release.commit` не пишется; сверку дожимает пересборка (одна попытка раз в 15 минут).
- **Клон перед сборкой** (`ops/publish.py --sync`): сборка берёт прошлый выпуск
  (`changes`, защита заголовка) и историю оценки из клона; отказ обновления — не
  провал, строка «ВНИМАНИЕ».

## 3. Такты

| Юнит | Когда (UTC) | Что делает |
|---|---|---|
| `t850-collect` | каждый день 05:20 (±5 мин), `Persistent` | обновление кода → зависимости → сбор двумя командами (`indicators.collect collect --only tinvest` с токеном, затем `--skip tinvest`: даты и формы ЦБ, ISS, ЦБ, новости, дозор, реестр дивидендов, ротация архива); отказал невосполнимый источник — повтор сбора внутри такта (до 3 попыток с паузой 3 мин) → по понедельникам тесты такта «в будущем» (+60 дней) → объём → здоровье (тревога) |
| `t850-release-watch` | будни 06:00–14:50 каждые 10 минут (09:00–17:50 МСК) | тихая проверка окна (календарь индикаторов, отложенное) → обновление кода → зависимости → дозор (`indicators.collect release-watch`: новости и документы эмитента) → что принято (`ops/tact.py news`) → при новом: нау-каст → тесты такта → клон данных → сборка → публикация → сверка |
| `t850-daily` | будни 19:00 (±5 мин), `Persistent` | обновление кода → зависимости → сбор рядов и цен (`daily-indicators`, сборщик T-Invest — отдельной командой с токеном) → нау-каст → здоровье (напоминание) → тесты такта → клон данных → сборка → публикация → сверка → объём |
| `t850-rebuild` | `*:02,17,32,47` | тихая проверка: дожим сверки прошлого такта; если код в `CODE_DIRS` (`model`, `indicators`, `ops`, `data/assumptions`, `data/facts`, `data/indicators`, `data/checks`, `requirements.txt`, без `*.md`) изменился с `release.commit` — тесты такта → клон данных → сборка → публикация → сверка, без сбора |

- **Расписание сдвинуто от соседей.** Сервер общий (4 ядра), и сборка выпуска
  занимает его на десятки минут, а две сборки разом растягивают обе: утренний сбор
  идёт через полчаса после панели Сбера (оба сборщика форм ходят на SOAP ЦБ с
  одного адреса, а на плотные серии ЦБ отвечает отказом), суточный такт — после
  суточных тактов соседних панелей, пересборка — на своих минутах. Перед включением
  таймеров времена сверяются со всем списком `systemctl list-timers` (раздел 5,
  шаг 13).
- **Дозор — дни МСФО и решений о дивидендах.** Окно дня релиза задаёт календарь
  индикаторов (`data/indicators/sources.yaml`, `data/facts/calendar.json`); вне
  окна проверка таймера выходит без строки. Месячные «Операционные результаты»
  эмитента — ряды, плитки и событие календаря: выпуск они не будят, их собирают
  плановые такты. Документы эмитента — PDF с текстовым слоем: распознавание не
  ставится.
- **Обновление кода** — `git fetch` + `reset --hard origin/main` и `exec` нового
  `run.sh` один раз за такт (иначе bash доигрывал бы прежний файл). GitHub не
  читается — такт идёт на текущем коде (утренний срез дороже свежести кода).
- **Зависимости** — по отметке `sha256(requirements.txt)` в venv, каждый такт до
  работы; отметка пишется только после удачного `pip install`, неудача — провал.
  Транзитивные пакеты закреплены в `requirements.txt` теми же версиями.
- **Env-файл читает `run.sh`, а не systemd.** Юнит передаёт только путь
  (`Environment=ENV_FILE=…`; строки `EnvironmentFile` в юнитах нет). `run.sh`
  читает файл (`set -a; . "$ENV_FILE"; set +a`) и сразу снимает `TINVEST_TOKEN` из
  окружения такта в неэкспортируемую переменную шелла.
- **Токен T-Invest — только сборщику T-Invest.** Токен передаётся одной команде —
  `indicators.collect <режим> --only tinvest`; остальные сборщики (`--skip tinvest`:
  чужой HTML и PDF), нау-каст, `pip`, тесты, сборка, публикация и мост тревог идут
  без токена (тест такта `tests/test_ops_run_sh.py`). Это гигиена окружения, а не
  граница доверия: env-файл читаем пользователем `dash`.
- **Тесты такта** — белый список по метке `tact` (`pytest.ini`), выражение
  `TACT_TESTS` в `run.sh`; ноль выбранных — провал. Быстрые тесты такта есть у
  каждого потока — ядро, книга, факты, индикаторы, витрина, контрольная модель,
  перезаякоривание, эксплуатация (сверяет `tests/test_ops_tact_suite.py`). Весь набор — не дольше
  270 с на сервере (`ops/budgets.json` → `tact_tests_target`; сверяется замером —
  итоговая строка pytest «N passed in T s» в шаге «тесты такта» журнала такта,
  раздел 9) и не дольше 150 с на ноутбуке (`tact_tests_laptop_limit`). Шаг CI
  «Тесты такта — замер времени» печатает `--durations` и краснеет после 300 с
  (`tact_tests_ci_ceiling`), а время дольше цели сервера печатает
  предупреждением. В CI набор сервера идёт один раз, своей частью: остальные
  тесты и тест мутаций — две другие части того же прогона, и ни один тест не
  идёт дважды. Сторож `tests/conftest.py` не даёт полному выпуску пробраться
  в такт.
- **Сроки данных в такт не входят.** Тест срока (метка `deadline`: объяснение
  сработавшего гейта действует на сегодня) выражение `TACT_TESTS` исключает; он
  идёт в CI и в ручном прогоне. Срок проверяет сама сборка (раздел 4): истёкшее
  объяснение сработавшего гейта — отказ, истекающее и истёкший срок документа
  эмитента — плашки выпуска. Поэтому набор сервера обязан быть зелёным на любой
  будущей дате: утренний такт по понедельникам гоняет его с «сегодня» + 60 дней,
  CI 1-го числа каждого месяца — весь набор без тестов сроков с + 180 дней.
  Красное «будущее» (тревога «тесты такта с FAKE_TODAY=… падают») — тест,
  привязанный к дате: это дефект теста, а не будильник данных.
- **Замок** один; утренний и суточный такты ждут его до `LOCK_WAIT_SECONDS` (=
  наибольший потолок пересборки и дозора), пересборка и дозор на занятом замке
  молча выходят с 0 — следующая проверка через 10–15 минут.
- **Дозор без потерь.** Принятое дозором (новый кандидат МСФО) ложится в
  `release_watch.pending` и снимается только после публикации: упавшая сборка не
  теряет релиз — его соберёт следующий такт дозора или суточный.

## 4. Коды и тревоги

**В штатном состоянии каждый такт кончается кодом 0.**

| Код юнита | Смысл | Повтор systemd |
|---|---|---|
| 0 | прошло (последняя строка журнала — «готово: …») | — |
| 1 | ПРОВАЛ шага, выпуска нет (в журнале «ПРОВАЛ на шаге «…» (код N). На витрине остаётся прежний выпуск.») | `daily`, `collect` — через 3 мин, не больше 3 стартов за окно (`StartLimitIntervalSec` юнита — часы), дальше юнит стоит до следующего таймера; дозор и пересборка — следующей проверкой |
| 8 | ТРЕВОГА: работа выполнена, выпуск (если такт его делает) на витрине; последняя строка — «ТРЕВОГА (код 8): <причины>» | нет — ни у одного такта (`RestartPreventExitStatus=8`): повтор тревогу не снимет |
| 64 | неверный режим или проба тревоги с источником не из такта | нет |
| 75 | замок держит другой такт дольше `LOCK_WAIT_SECONDS` | да, в том же окне |
| 78 | нет env-файла, в нём нет `TTECH_REPO_DIR`/`BANK_STATE_DIR`, каталога кода `TTECH_REPO_DIR` нет (опечатка в пути) или он не клон git (в нём нет `.git`: такт не отдаёт `git fetch` и `git reset --hard` репозиторию выше) | нет |

**Окно перезапуска.** systemd отсчитывает `StartLimitIntervalSec` от первого старта
и окно не двигает, поэтому оно обязано вмещать три самых долгих прогона с паузами:
`StartLimitIntervalSec` = 3 × (`RuntimeMaxSec` + `RestartSec` + 90 с на
`ExecStopPost`), считается из `ops/budgets.json` (`restart`), равенство сверяет
`tests/test_ops_units.py`; окна в часах печатает `python ops/tools/budgets.py`.
Окно обязано быть короче суток — иначе оно заперло бы и завтрашний запуск по
таймеру: бюджет с окном длиннее инструмент не принимает (строка «бюджет: restart
…»). Стойкий отказ (гейт, защита заголовка, отозванный ключ)
даёт три прогона и стоп: `systemctl status` покажет `start-limit-hit`, следующий
запуск — по таймеру; раньше — `sudo systemctl reset-failed t850-<такт>.service`.

**Три исхода** (docs/INTERFACES.md §6). Отказ — выпуска нет, на витрине прежний.
Тревога — то, что требует человека и что повтор не снимет; повтор — только там,
где он спасает данные. Плашка — срок, о котором достаточно знать заранее: она
печатается в выпуске и на витрине, такт о ней не тревожит.

**Сборка выпуска** (`python -m model.build_release`):

| Код сборки | Что | Такт |
|---|---|---|
| 0 | выпуск собран — в том числе с плашками: объяснение сработавшего гейта истекает в ближайшие 30 дней (флаг `explanation_expiring`: гейт и дата); срок документа эмитента истёк (флаг `policy_expired`: срок дивидендной политики — «действует прежняя до новой») | публикация, код такта 0 |
| 3 | выпуск собран, но требует человека: деградировал живой вход оценки (цена не принята, запись реестра не принята, кривая или ключевая не приняты) или источник, уже получивший код 3 у сборщиков; флаг `dividend_register` — нет записи реестра объявленных дивидендов за период к сроку; выпуск от 400 000 байт | публикация, в конце — «ТРЕВОГА (код 8): сборка подняла тревогу …» |
| 1 | выпуск не собран: нарушен инвариант или контракт; сработавший гейт без действующего объяснения — нет записи, срок истёк или **масса вне коридора ожидания** (MODEL §14.2); защита заголовка; нет цены главного тикера | «ПРОВАЛ на шаге «сборка выпуска»», на витрине прежний выпуск |

Масса гейта вне коридора — отказ, а не тревога: объяснение с другой массой уже
не объясняет то, что сработало. Лечится правкой `expected_mass`/`expected_mass_range`
в `data/assumptions/gate_explanations.yaml` (с текстом, почему) или причины.
Истёкшее объяснение сработавшего гейта лечится новой записью объяснения со сроком
или перезаякориванием (docs/MANUAL.md §10.4, §10.9); плашка `explanation_expiring`
появляется за 30 дней до этого. У сроков ручных входов — миры после заседания
Банка России с прогнозом, отчёт МСФО, запись реестра после решения собрания,
замена оценки нормативов фактом формы — плашки нет: сработавший гейт
`manual_input_overdue` останавливает сборку сразу, и сборка называет только гейт.
Какой вход просрочен, календарь ближайших отказов с датами и проверка сборки на
любую будущую дату — docs/MANUAL.md §10.9.

**Сбор источников** (`python -m indicators.collect <режим>`):

- **Невосполнимый источник** (винтажи форм ЦБ, снимки T-Invest, новости и документы
  дня релиза) отказал: сборщики отвечают кодом 3 и ставят в `collector_report.json`
  `retry: true`. Утренний такт в этом и только в этом случае повторяет сбор сам,
  внутри прогона, — всего до 3 попыток с паузой 3 мин (`ops/budgets.json` →
  `collect_retry`); не добрал — «ТРЕВОГА (код 8): невосполнимый источник не собран
  (попыток: 3 …)». Суточный такт и дозор сбор не повторяют.
- **Источник без токена** — тревога без повтора: повтор токена не добавит.
- **Восполнимый источник**, питающий только плитки и наблюдения, деградировал: до
  третьего такта подряд — код 0, строка «деградация (такт k из 3)» в журнале и
  причина в выпуске (`live.degraded`, плитка); с третьего — тревога «сбор требует
  внимания …». Счётчик считается раз за день и сбрасывается первым удачным
  сбором. **Такты со сборкой судят источники тем же счётчиком:** сборка поднимает
  тревогу только по живым входам оценки и по источникам, уже получившим код 3 у
  сборщиков, — причина моложе трёх тактов тревогой не становится.
- **Критический источник** (запасной путь цен и кривой): отказ — код 1, провал
  шага, повторяет systemd в пределах окна; его деградация — тревога сразу.
- Тревога реестра дивидендов, тяжёлый выпуск, дерево ветки данных у порога,
  несостоявшаяся сверка, красное «будущее» — тревога сразу, без повтора.

Внутри такта шаги отвечают кодом 3 «сделано, но требует внимания» (невосполнимый
источник не добран или сбор требует внимания, тревога сборки, нау-каст записан не
целиком, публикация с замечанием, сверка не дождалась выпуска, красное «будущее»);
причины копятся и уходят одним кодом 8 в конце — последняя строка «ТРЕВОГА (код 8): …».
Других кодов тревоги у такта нет. Любой другой ненулевой код шага превращается в
1. Пересборка на коммите, где она уже падала, выходит с 1 без работы: «упало»
пришло один раз.

**Что видно в журнале такта** (`journalctl -u t850-<такт>` и
`logs/<дата>.log`): шапка «Т-Технологии 850 · такт … · время · каталог», затем шаги
строками «── шаг ── чч:мм:ссZ» (по ним меряются потолки), строки сборщиков,
сборки и публикации («выпуск <sha12> …», «отправлено в release», «СВЕРКА: …»,
«ПУБЛИКАЦИЯ: …»), и последняя строка — «готово: …», «ТРЕВОГА (код 8): …» или
«ПРОВАЛ на шаге «…» (код N)».

Мост `dash-alert` зовётся из `ExecStopPost` всегда и шлёт смену состояния: «упало»
и «снова проходит». **Стоящая тревога держит юнит в «упало»:** новая причина при
стоящей тревоге сообщения не даст — её читают в журнале такта (последняя строка
«ТРЕВОГА (код 8): …» называет все причины прогона). Поэтому код 8 оставлен тому,
что действительно требует человека, а сроки данных ушли в плашки. Панель
регистрируется строкой у `dash-watch` (адрес двери, порог свежести по
`Last-Modified`) и веткой в `dash-alert` — по процедуре служебного репозитория
панелей. Выпуск с тем же хэшем не публикуется повторно, и `Last-Modified` не
двигается, пока не меняются цена или входы: порог сторожа — с запасом на выходные
и праздники без торгов.

**Проба доставки тревоги.** Мост `dash-alert` зовётся только из `ExecStopPost`
юнита, поэтому проба идёт через systemd — временной вставкой юнита (живёт в
`/run`, до перезагрузки): утренний такт проходит как обычно, а в конце названный
невосполнимый источник объявляется отказавшим — код 8 по боевому пути.

```bash
sudo systemctl edit --runtime t850-collect.service
#   во вставке — три строки:
#   [Service]
#   Environment=TTECH_SIMULATE_FAILURE=cbr_forms
#   Restart=no
sudo systemctl --wait start t850-collect.service
systemctl show -p ExecMainStatus t850-collect.service    # ExecMainStatus=8
journalctl -u t850-collect -n 5 --no-pager                 # «ТРЕВОГА (код 8): … ПРОБА ТРЕВОГИ: источник cbr_forms объявлен отказавшим …»
sudo rm -r /run/systemd/system/t850-collect.service.d && sudo systemctl daemon-reload
```

В Telegram обязано прийти сообщение с именем панели — оно и проверяет ветку
панели в мосте. Вставку снимать именно удалением каталога из `/run`:
`systemctl revert` снял бы и постоянные вставки. `Restart=no` — чтобы проба не
повторялась, если такт кончится провалом шага. Следующий плановый утренний такт
обязан прислать «снова проходит». Имя не из невосполнимых источников такта — код
64 без работы. Запуск `run.sh` руками (`sudo -u dash env ENV_FILE=… TTECH_SIMULATE_FAILURE=…
bash ops/run.sh collect`) мост не зовёт: им проверяются только коды 8 и 64.

## 5. Установка на сервер (по шагам)

Сервер — шаблон панелей владельца: пользователь `dash` с домашним каталогом
`/srv/dash`, общие скрипты `dash-alert` и `dash-watch`. Панель занимает три места:
код `/srv/dash/repo-850-t`, состояние `/var/lib/t-850`, настройки
`/usr/local/etc/t-850/env`. Команды — под служебным пользователем с `sudo`;
значения с доступами (адрес сервера, имя файла ключа, ssh-алиас, токен) — в
справочнике владельца вне репозитория, здесь они стоят в угловых скобках.

Порядок обязателен: первый сбор → замер сборки руками и бюджет из него → юниты →
первый выпуск в ветке → GitHub Pages → витрина → таймеры. Сборка без собранных цен
не выходит; юнит с потолком ниже настоящего времени сборки убивает её на середине;
без выпуска в ветке боевой адрес отвечает 503. До установки: оба публичных
репозитория созданы, код опубликован первым push (раздел 12), проект Pages создан
(шаг 12). На сервере уже
работают соседние панели, поэтому часть шагов сводится к проверке (пакет venv,
ключ хоста GitHub); команда шага безвредна и при повторе. Юниты, каталоги и
env-файл соседних панелей шаги не трогают: у этой панели имена свои (`t850-*`,
`t-850`), и каждая ручная команда называет путь именно её env-файла.

Помощник для команд слоя ops — под пользователем конвейера, с настройками
env-файла и **без токена T-Invest** (токен нужен только пробе источников, шаг 6, и
первому сбору, шаг 7, — там его раздаёт сам такт):

```bash
ops850() { sudo -u dash bash -c 'set -a; . /usr/local/etc/t-850/env; set +a; unset TINVEST_TOKEN; cd /srv/dash/repo-850-t && exec "$@"' ops850 "$@"; }
```

Функция живёт в той оболочке, где задана: в новом сеансе и в каждом окне `tmux` её
задают заново. Команды раздела запускаются из каталога, доступного пользователю
`dash` (например, `cd /`): часть из них исполняется от его имени, а из закрытого
домашнего каталога оператора git отвечает отказом чтения текущего каталога.

1. **Код и окружение.**
   ```bash
   dpkg -s python3.12-venv | grep -c '^Status: install ok installed'   # 1; на новой машине — apt-get install
   sudo -u dash git clone --single-branch --branch main \
        https://github.com/ML371KL/temp-zero-inode-850-t.git /srv/dash/repo-850-t
   sudo -u dash python3.12 -m venv /srv/dash/repo-850-t/.venv
   sudo -u dash /srv/dash/repo-850-t/.venv/bin/pip install -q -r /srv/dash/repo-850-t/requirements.txt
   ```
   Проверка:
   `sudo -u dash /srv/dash/repo-850-t/.venv/bin/python -c 'import yaml, pdfplumber, pypdfium2; print("ok")'`.
   Пакеты Python нужны уже пробе источников (шаг 6), до первого такта. Дальше их
   держит такт по отметке `.venv/.requirements.sha256`; отметку руками не писать —
   первый такт поставит её сам (перенаправление `>` выполнила бы оболочка без прав
   `dash`). Распознавание PDF этой панели не нужно: документы эмитента — с текстовым
   слоем, системные пакеты распознавания не ставятся.
2. **Настройки.** Файл создаётся из образца, только если его ещё нет (готовый
   файл с токеном команда не трогает); каталог настроек, заведённый заранее,
   первая команда лишь приводит к владельцу и режиму `root:dash 750`:
   ```bash
   sudo install -d -o root -g dash -m 750 /usr/local/etc/t-850
   sudo test -e /usr/local/etc/t-850/env || \
        sudo install -o root -g dash -m 640 /srv/dash/repo-850-t/ops/env.example /usr/local/etc/t-850/env
   sudoedit /usr/local/etc/t-850/env
   ```
   В образце только имена — значения вписываются здесь:
   `TTECH_REPO_DIR=/srv/dash/repo-850-t`, `BANK_STATE_DIR=/var/lib/t-850`
   (без них — код 78); `TINVEST_TOKEN` — токен T-Invest «только чтение» (секрет:
   только в env-файлах сервера), выпущенный на отдельный счёт без активов, а не на
   основной счёт владельца: токен «только чтение» открывает портфель и операции
   того счёта, на который выпущен. Токен один на обе панели банков
   (`docs/DECISIONS.md`): его строка переносится из env-файла панели Сбера
   командой ниже, без вывода значения; `TTECH_RELEASE_REMOTE` — ssh-алиас deploy-ключа вида
   `<алиас>:ML371KL/temp-zero-inode-850-t-data.git`; `TTECH_GIT_NAME` и
   `TTECH_GIT_EMAIL` — noreply-адрес из `.github/commit-emails.allow`;
   `TTECH_PUBLIC_URL` — пусто (дверь по умолчанию) или адрес двери. Необязательные:
   `BANK_DATA_REPO_DIR` (без нужды не задавать: каталог охраняется, раздел 2), `TTECH_VENV`, `TTECH_PYTHON`, `TTECH_VERIFY_TIMEOUT`,
   `TTECH_VERIFY_PAUSE`, `TTECH_PUSH_BACKOFF`, `TTECH_FUTURE_WEEKDAY`,
   `TTECH_FUTURE_DAYS`. `BANK_WORKERS` — процессов полосы в сборке: то же число,
   что `workers` в `ops/budgets.json` (его подтверждает замер шага 8); пока строка
   пуста, такт берёт число бюджета сам. Имена — раздел 11.

   Перенос токена (путь env-файла панели Сбера — в её инструкции по эксплуатации;
   после правки владелец и права файла возвращаются явно):
   ```bash
   sudo sh -c 'f=/usr/local/etc/t-850/env; s="<env-файл панели Сбера>"
        sed -i "/^TINVEST_TOKEN=/d" "$f"; grep -m1 "^TINVEST_TOKEN=" "$s" >> "$f"
        chown root:dash "$f"; chmod 640 "$f"; grep -c "^TINVEST_TOKEN=" "$f"'      # 1
   ```
   Проверка — печатаются только имена, значения не выводятся:
   ```bash
   sudo stat -c '%U:%G %a' /usr/local/etc/t-850/env      # root:dash 640
   sudo -u dash bash -c 'set -a; . /usr/local/etc/t-850/env; set +a
        for v in TTECH_REPO_DIR BANK_STATE_DIR TINVEST_TOKEN TTECH_RELEASE_REMOTE TTECH_GIT_NAME TTECH_GIT_EMAIL; do
          [ -n "${!v}" ] && echo "$v задана" || echo "$v ПУСТА"; done'
   ```
   **Кто читает файл.** Юниты systemd env-файл не читают: в них стоит только путь
   (`Environment=ENV_FILE=/usr/local/etc/t-850/env`), строки `EnvironmentFile`
   нет — иначе токен лежал бы в окружении всего юнита, включая мост тревог. Файл
   читает `ops/run.sh`; он сразу снимает `TINVEST_TOKEN` из окружения такта и
   передаёт его одной команде — сборщику T-Invest (раздел 3). Поэтому и ручные
   команды установки идут через помощник `ops850` — без токена.
3. **Ключ записи в репозиторий данных.** Публичный репозиторий данных создаётся
   на GitHub до ключа (ветку `release` создаст шаг 5 — он ходит уже через
   ssh-алиас ключа). Отдельный deploy-ключ ed25519 в каталоге `/srv/dash/.ssh/`
   (имя файла и алиас — в справочнике владельца); если ключа ещё нет:
   ```bash
   sudo -u dash ssh-keygen -t ed25519 -N '' -C 't-850-data' -f /srv/dash/.ssh/<файл ключа>
   ```
   Открытая часть (`<файл ключа>.pub`) — в **репозиторий данных**: Settings →
   Deploy keys → Allow write access. В репозиторий кода ключ не добавляется
   никогда: код сервер берёт анонимно. В `/srv/dash/.ssh/config` — алиас:
   ```
   Host <алиас>
       HostName github.com
       User git
       IdentityFile /srv/dash/.ssh/<файл ключа>
       IdentitiesOnly yes
   ```
   Ключ хоста GitHub — заранее в `/srv/dash/.ssh/known_hosts`: под
   `ProtectSystem=strict` каталог только для чтения, и ssh в юните его не допишет
   (`BatchMode=yes` — будет отказ, не вопрос). На общем сервере строка уже есть;
   если её нет (отпечаток сверить с опубликованным GitHub):
   ```bash
   sudo -u dash sh -c 'ssh-keygen -F github.com -f /srv/dash/.ssh/known_hosts >/dev/null ||
        ssh-keyscan -t ed25519 github.com >> /srv/dash/.ssh/known_hosts'
   sudo -u dash ssh-keygen -lf /srv/dash/.ssh/known_hosts
   ```
   Проверка: `sudo -u dash ssh -T <алиас>` — «Hi ML371KL/temp-zero-inode-850-t-data!
   You've successfully authenticated…» (код возврата ssh при этом 1 — так отвечает GitHub).
   Ключ и алиас могли быть заведены заранее, вместе с репозиторием данных, — тогда
   шаг сводится к проверкам: `ssh -T` отвечает именем репозитория данных, а
   ```bash
   sudo -u dash ssh -G <алиас> | grep -E '^(hostname|user|identityfile|identitiesonly) '
   ```
   называет `github.com`, `git`, файл ключа и `yes`. Ответ `ssh -T` с именем другого
   репозитория — алиас смотрит на ключ соседней панели: публикация с ним не пройдёт.
4. **Правила (rulesets).** Репозиторий кода: `main` — запрет force-push и удаления,
   пишет только владелец. Репозиторий данных: `release` — запрет удаления и
   force-push (публикация только дописывает коммиты).
5. **Каталог состояния и ветка данных** — один раз: в публичном
   `temp-zero-inode-850-t-data` ветка `release` (осиротевшая, `.nojekyll`):
   ```bash
   sudo install -d -o dash -g dash -m 750 /var/lib/t-850
   ops850 .venv/bin/python ops/publish.py --init
   ```
   Ответ — «ветка release создана: один коммит с .nojekyll» или «ветка release уже
   есть — создавать нечего»; код 0. Каталог состояния мог быть создан раньше —
   первая команда приводит его владельца и режим к `dash:dash 750`; дальше режим
   держит юнит (`StateDirectoryMode=0750`), проверка — в шаге 10.
6. **Проба источников** с сервера — до таймеров. Единственная ручная команда с
   токеном (проверяется и дорога T-Invest):
   ```bash
   sudo -u dash bash -c 'set -a; . /usr/local/etc/t-850/env; set +a;
        cd /srv/dash/repo-850-t && .venv/bin/python ops/tools/probe.py --pdf "<адрес PDF последнего пресс-релиза эмитента>"'; echo "код $?"
   ```
   Таблица: ISS, ЦБ (SOAP DailyInfo, CreditOrgInfo — 4 метода по регномеру,
   avgprocstav, `/dataservice`), статический PDF эмитента, T-Invest (TLS с
   закреплённым корнем, ShareBy с токеном). Адрес PDF на свежем сервере задаётся
   явно: ссылка последнего пресс-релиза со страницы пресс-релизов эмитента (хост —
   из `data/indicators/sources.yaml`); позже проба берёт последний адрес дозора
   сама. Здесь же впервые проверяется, что документы эмитента отдаются серверу.
   Код 0 — все прошли; строка «НЕТ» называет причину. Пробу и первый сбор
   (шаг 7) не запускать вплотную к тактам панели Сбера: раз в неделю она
   перекачивает последние даты форм ЦБ, а на плотные серии запросов с одного
   адреса ЦБ отвечает отказом.
7. **Первый сбор — до первой сборки**, руками и вне systemd: юниты ещё не стоят
   (их потолки даст шаг 8). Без собранной цены главного тикера сборка не выходит,
   поэтому сначала утренний такт целиком:
   ```bash
   sudo -u dash env ENV_FILE=/usr/local/etc/t-850/env bash /srv/dash/repo-850-t/ops/run.sh collect; echo "код $?"
   ```
   Токен такт раздаёт сам — только сборщику T-Invest, как и под юнитом (раздел 3).
   Годный итог — последняя строка «готово: …» и код 0; в понедельник такт заодно
   гоняет тесты такта «в будущем». Код 8 — причины в строке «ТРЕВОГА (код 8): …»
   разбираются по разделу 4 до следующего шага. Тревоги реестра дивидендов на
   пустом состоянии не бывает: дивиденд, выплаченный до даты книги, закрывает
   стартовый реестр фактов (`docs/INDICATORS.md` §8a). Мост тревог ручной запуск не
   зовёт — сообщений в Telegram от него нет.
8. **Замер сборки руками — до юнитов и до таймеров.** Потолки юнитов
   (`RuntimeMaxSec`, `MemoryHigh`, `MemoryMax`) и число процессов полосы стоят на
   времени и памяти сборки; до этого шага в `ops/budgets.json` — оценка по замеру
   ноутбука (`status: estimate`), а под юнитом с заниженным потолком сборку убил бы
   systemd. Вне systemd меряются сборка при двух и при четырёх процессах полосы,
   сборка в худшем по времени случае и набор тестов такта:
   ```bash
   for n in 2 4; do
     ops850 env BANK_WORKERS=$n .venv/bin/python ops/tools/measure.py -- .venv/bin/python -m model.build_release
   done
   W=4                                   # число процессов, выбранное по двум замерам выше
   ops850 env BANK_WORKERS=$W .venv/bin/python ops/tools/measure.py -- .venv/bin/python ops/tools/worst_build.py
   TACT=$(sudo -u dash sed -n 's/^TACT_TESTS="\(.*\)"$/\1/p' /srv/dash/repo-850-t/ops/run.sh)
   if [ -n "$TACT" ]; then ops850 .venv/bin/python ops/tools/measure.py -- .venv/bin/python -m pytest -m "$TACT"
   else echo "ОТКАЗ: выражение такта не прочитано — замер тестов не запускать"; fi
   ```
   Каждый замер кончается строкой «замер: N с; пик памяти дерева M МБ (…),
   наибольший процесс K МБ; BANK_WORKERS=n; код команды C». Сборка пишет выпуск
   только в каталог состояния и ничего не публикует; её код 0 или 3 (тревоги
   названы строками «тревога:»), код 1 — отказ сборки, он разбирается по разделу 4
   до продолжения. Пустое выражение такта отдало бы pytest весь набор — с сетью и
   тестом мутаций, — поэтому замер тестов идёт только под условием.

   **Худший случай.** Время сборки зависит от цены: строка обратного расчёта из
   списка книги (`valuation.reverse_dcf.refine_rows`; без ключа — любая), у которой
   решение попадает в диапазон книги, уточняется на полной полосе, и чем ближе
   цена к медиане оценки, тем больше таких строк. `ops/tools/worst_build.py`
   собирает выпуск в памяти (ничего не пишет) на цене чуть выше и чуть ниже
   медианы и кончается строкой «худший случай: сборка не дольше N с» — временем
   сборки, достроенным до полного числа шагов уточнения у каждой такой строки. На
   этом числе, а не на времени сборки по цене дня, стоит бюджет (раздел 9).

   Замеры долгие (ожидаемое время сборки — таблица `python ops/tools/budgets.py`;
   при двух процессах — вдвое дольше, чем при четырёх; худший случай — две сборки
   подряд, каждая в несколько раз дольше сборки по цене дня): запускать в `tmux`
   или `screen`, чтобы обрыв соединения не оборвал замер.

   Числа — в бюджет, на ноутбуке, одной правкой `ops/budgets.json`: `status:
   measured` и `measured_on`; в `basis` — замер сервера: `machine`, `measured_on`,
   `workers` и `build_s` выбранного числа процессов, `build_worst_s` (число строки
   «худший случай»), `memory_tree_mb`, `memory_process_mb`, `tact_tests_s`,
   `tact_tests_memory_mb`. Три замера — `build_s`, `build_worst_s` и
   `memory_tree_mb` — пишутся числом или списком прогонов; три других —
   `memory_process_mb`, `tact_tests_s` и `tact_tests_memory_mb` — одним числом
   (наибольший из прогонов): список в них инструмент не примет. Запасы оценки
   `basis.server_factor` и `basis.tact_server_factor` из `basis` снимаются — замер
   уже с сервера.

   **Выбор числа процессов.** `workers` — число процессов, при котором сборка
   укладывается в цель, память — в `MemoryHigh` с запасом, а окно перезапуска
   суточного такта остаётся короче суток. Сборка при двух процессах идёт вдвое
   дольше, а окно перезапуска — три потолка такта с паузами (раздел 4): бюджет, у
   которого оно выходит за сутки, инструмент не принимает — строка «бюджет: restart
   …», производные числа не пишутся. Тогда замер при двух процессах остаётся
   справочным (память на процесс), а в бюджет идёт замер при четырёх.
   `seconds.build` — не ниже худшего случая, `seconds.tact_tests` — замер набора,
   `memory` — по замеру. Затем одна перегенерация и проверка:
   ```bash
   python ops/tools/budgets.py --write      # потолки юнитов, LOCK_WAIT_SECONDS, BUDGET_WORKERS, потолки CI
   python ops/tools/budgets.py              # таблица: шаги, потолки, окна перезапуска, память
   python -m pytest tests/test_ops_units.py tests/test_ops_ci.py
   ```
   Бюджет, который противоречит своему замеру, инструмент называет строками
   «бюджет: …» и производных чисел не трогает. Правка уходит в `main` обычным
   порядком (раздел 7): прогон CI на ней полный, его конца ждут — десятки минут.
   На сервере — новый код и то же число процессов в env-файле:
   ```bash
   sudo -u dash git -C /srv/dash/repo-850-t pull --ff-only
   sudoedit /usr/local/etc/t-850/env                                  # строка BANK_WORKERS=<workers бюджета>
   sudo grep -c '^BANK_WORKERS=[1-7]$' /usr/local/etc/t-850/env      # 1
   sudo stat -c '%U:%G %a' /usr/local/etc/t-850/env                   # root:dash 640
   ```
   **Цели.** Набор тестов такта на сервере — не дольше 270 с (`tact_tests_target`):
   замер дольше цели бюджет не примет — метка `tact` снимается с самых долгих
   тестов (они остаются в CI), замер повторяется. Сборка в худшем случае — не
   дольше 30 минут (`build_target`, цель полного выпуска на сервере); дольше
   45 минут при четырёх процессах (`build_stop`) — до включения таймеров это
   решает ведущий: строки обратного расчёта, уточняемые на полной полосе, число
   прогонов полосы и подвыборка — ключи книги. Между целью и этим порогом установка
   продолжается, а инструмент бюджета напоминает о цели строкой «ВНИМАНИЕ». Цель
   рабочей машины — отдельные числа бюджета (`build_laptop_goal`): полный выпуск
   при четырёх процессах полосы — не дольше 15 минут в обычном случае и 25 минут в
   худшем. На сервере она не меряется: её сверяет инструмент бюджета с замером
   рабочей машины, пока бюджет — оценка (раздел 9).
9. **Юниты** — из копии с числами шага 8:
   ```bash
   sudo sh -c 'install -o root -g root -m 644 /srv/dash/repo-850-t/ops/systemd/* /etc/systemd/system/'
   sudo systemctl daemon-reload
   systemctl show -p EnvironmentFiles -p Environment t850-daily.service
   grep -H '^RuntimeMaxSec=\|^MemoryHigh=\|^MemoryMax=\|^StateDirectoryMode=' /etc/systemd/system/t850-*.service
   ```
   Проверка: `EnvironmentFiles=` пуст, в `Environment=` — только `ENV_FILE=…` и
   `PYTHONUNBUFFERED=1`; потолки времени и памяти установленных юнитов — те, что
   печатает `python ops/tools/budgets.py`, режим каталога состояния — `0750`. Юниты
   прежней выкладки (если стояли) этой же командой заменяются целиком; юниты
   соседних панелей она не трогает — ставятся только файлы `t850-*` этой копии.
10. **Первый выпуск через юниты** (видно все шаги; утренний такт повторяет сбор
    шага 7 уже под защитой юнита):
    ```bash
    sudo systemctl start --wait t850-collect.service; systemctl show -p ExecMainStatus t850-collect.service
    sudo systemctl start --wait t850-daily.service;   systemctl show -p ExecMainStatus t850-daily.service
    journalctl -u t850-daily -n 40 --no-pager
    sudo stat -c '%U:%G %a' /var/lib/t-850                       # dash:dash 750 — режим держит юнит
    ```
    Утренний такт — `ExecMainStatus=0`. Суточный кончится кодом 8 с одной причиной —
    «выпуск отправлен в репозиторий данных, но боевая дверь не подтвердила его»:
    Pages ещё не включён, витрина не выложена — это ожидаемо, выпуск уже в ветке
    `release`. Сверка перед этим ждёт дверь всё своё окно (10 минут), а мост тревог
    пришлёт сообщение об упавшем юните — тоже ожидаемо. Любая другая причина в
    строке «ТРЕВОГА (код 8): …» или «ПРОВАЛ на шаге …» разбирается по разделу 4 до
    включения таймеров. Время шага «сборка выпуска» в журнале (строки «── шаг ──
    чч:мм:ссZ») и пик памяти юнита (строка systemd «… memory peak» по окончании
    прогона) сверяются с замером шага 8.
11. **GitHub Pages репозитория данных**: Settings → Pages → Deploy from a branch →
    `release`, `/ (root)`. Через 1–3 минуты адрес раздачи отдаёт выпуск:
    `curl -sI https://ml371kl.github.io/temp-zero-inode-850-t-data/latest.json | head -1`
    — `200`. Actions в репозитории данных не выключать: на них держится сборка Pages.
12. **Витрина и приёмка выпуска.** Проект Pages `tzi-850-t` создаётся один раз
    — в панели Cloudflare или через API, производственная ветка `main` (команда
    wrangler для создания проекта не годится: она заводит Worker, а не проект
    Pages, docs/DASHBOARD.md §8); первая команда шага проверяет, что проект есть.
    ID аккаунта и токен Cloudflare живут в учётной записи wrangler на ноутбуке и
    в репозиторий не пишутся. С ноутбука, из корня рабочей копии на коммите `main`:
    ```bash
    npx wrangler@4.135.0 pages project list          # в списке есть tzi-850-t
    npx wrangler@4.135.0 pages deploy web --project-name tzi-850-t --branch main
    curl -sI -A tzi-850-t-check/1.0 https://tzi-850-t.pages.dev/api/model | grep -iE '^(HTTP|x-data-source)'
    ```
    Дверь отвечает `200` и `x-data-source: pages`. Затем на сервере сверку
    дожимает пересборка — руками (таймеры ещё не включены):
    ```bash
    sudo systemctl start --wait t850-rebuild.service; systemctl show -p ExecMainStatus t850-rebuild.service
    journalctl -u t850-rebuild -n 20 --no-pager | grep 'СВЕРКА: .* пройдена'
    sudo cat /var/lib/t-850/release.commit; sudo -u dash git -C /srv/dash/repo-850-t rev-parse HEAD
    sudo test ! -e /var/lib/t-850/release.pushed && echo "отметка сверки снята"
    ```
    **Приёмка установки — не по коду первого такта, а по трём признакам:** в
    журнале есть строка «СВЕРКА: выпуск <sha12> · … — пройдена …»;
    `release.commit` равен коммиту кода на сервере; отметка `release.pushed`
    снята. Суточный юнит после шага 10 остаётся в «упало» до своего следующего
    прогона — он кончится кодом 0 (можно запустить сразу:
    `sudo systemctl start --wait t850-daily.service`). Команду
    `ops/publish.py --verify` без окружения сервера не запускать: она прочла бы
    пустое состояние рабочей копии и ответила «сверять нечего» с кодом 0 — ложное
    «сверено».

    Текст экранов на первом живом выпуске — с ноутбука, тем же Node, что у
    wrangler (на выпуске из фикстуры эту проверку гоняет CI):
    ```bash
    curl -s -A tzi-850-t-check/1.0 https://tzi-850-t.pages.dev/api/model -o var/first-release.json
    node tests/web/web_release_text.mjs var/first-release.json | tail -n 3; echo "код ${PIPESTATUS[0]}"
    ```
    Годный итог — `"failed": []` и код 0: на шести экранах нет служебного текста
    (имён полей и методов API, рабочих пометок, дат без года). Отказ называет экран,
    правило и образец строки; правится источник строки в фактах или книге, не витрина.
13. **Таймеры** — последними, когда приёмка шага 12 пройдена и юниты стоят с
    потолками из замера:
    `sudo systemctl enable --now t850-collect.timer t850-release-watch.timer t850-daily.timer t850-rebuild.timer`;
    проверка — `systemctl list-timers 't850-*'` (четыре строки) и весь список
    `systemctl list-timers`: времена этой панели не совпадают с тактами соседних.
14. **Сторож и мост — делает владелец.** Регистрация панели у общего моста тревог
    и сторожа свежести сервера идёт по процедуре служебного репозитория панелей
    (раздел 4): ветка панели в `dash-alert`, строка у `dash-watch` с адресом двери и
    порогом свежести. Правка общих скриптов сервера затрагивает все панели,
    поэтому шаг не входит в установку конвейера и исполняется владельцем. До
    регистрации тревоги юнитов приходят под родовым именем юнита, а свежесть
    панели сторож не проверяет — остановившиеся таймеры никто не заметит: раз в
    неделю смотреть `systemctl list-timers 't850-*'` и `Last-Modified` двери
    (раздел 10). После регистрации — проба доставки тревоги через юнит (раздел
    4): сообщение в Telegram с именем панели и «снова проходит» после следующего
    утреннего такта. Если следующий утренний такт — понедельничный и «будущее»
    красное, «снова проходит» не придёт: причина — в его журнале, это дефект
    теста (раздел 3).

## 6. Откат

```bash
sudo -u dash env ENV_FILE=/usr/local/etc/t-850/env \
     bash /srv/dash/repo-850-t/ops/run.sh rollback <sha выпуска, от 12 знаков> "причина"
```

Под тем же замком, что и такты: `latest.json` перезаписывается выпуском
`releases/<sha>.json` с НОВЫМ `published_at` (со старым сторож сразу объявил бы
панель мёртвой), в `history.json` — строка `rollback` с причиной (третий
аргумент; без него — «откат с <прежний sha12>»), затем сверка. Список выпусков —
`history.json` и `ls releases/` в
`/var/lib/t-850/data-repo`. Ничего не удаляется; `release.commit` откат назад
не двигает. Если откатывают выпуск, чья сверка ещё не завершена (отметка
`release.pushed` висит), откат записывает в `release.commit` код этого выпуска:
иначе пересборка сочла бы код новым и за 15 минут вернула бы выпуск поверх отката.
Откат — пауза на один такт, а не состояние: ближайший выпуск (суточный
такт, дозор или пересборка на новом коммите) перепишет указатель. Если причина не
устранена — остановить таймеры:
`sudo systemctl stop t850-daily.timer t850-release-watch.timer t850-rebuild.timer`.

## 7. Выкладка кода и юнитов

Код попадает на сервер только через `main`: рабочая ветка → CI зелёный →
fast-forward `main` → ближайшая пересборка (`*:02,17,32,47`) публикует выпуск на
новом коде. Если меняются сами юниты: остановить таймер пересборки, поставить
юниты из обновлённой копии (`install … /etc/systemd/system/`), `daemon-reload`,
запустить таймер. Пересборка идёт под потолком УСТАНОВЛЕННОГО юнита. Потолки
времени и памяти в юнитах руками не правятся: это производные бюджета — правка
`ops/budgets.json` и `python ops/tools/budgets.py --write` (раздел 9). Новый
бюджет доходит до сервера только с переустановкой юнитов; число процессов полосы
такт берёт из нового кода сам (если `BANK_WORKERS` в env-файле стоит числом —
привести его к `workers` бюджета).

## 8. Витрина

```bash
npx wrangler@4.135.0 pages deploy web --project-name tzi-850-t --branch main
```

Из рабочей копии на коммите `main` (функции wrangler берёт из `functions/`). Проект
Pages `tzi-850-t` создаётся один раз (раздел 5, шаг 12); проверка —
`npx wrangler@4.135.0 pages project list`. Метка `--branch` обязана совпадать с
производственной веткой проекта (`main`), иначе выкладка молча уйдёт в
предпросмотр. Меняется контракт — сначала данные (выпуск с новыми полями), потом
витрина (PAYLOAD §8). Локальный предпросмотр с боевой CSP —
`python ops/tools/devserver.py <порт> <выпуск.json>` (docs/DASHBOARD.md §7–8).

## 9. Потолки времени и бюджеты

- **Один файл — `ops/budgets.json`.** В нём и только в нём числа бюджета пишутся
  руками: время шагов тактов на сервере (`seconds`), запас (`safety`), число
  процессов полосы (`workers`), память юнитов (`memory`), время частей набора
  тестов для CI (`ci`), замер, на котором всё это стоит (`basis`). Производные —
  `RuntimeMaxSec`, `StartLimitIntervalSec`, `MemoryHigh` и `MemoryMax` юнитов,
  `LOCK_WAIT_SECONDS`, `COLLECT_RETRY_*` и `BUDGET_WORKERS` в `run.sh`, потолки
  заданий CI — считаются из него (формулы — поле `about`) и лежат строками в
  своих файлах. **Смена чисел — одна правка файла и одна команда:**
  ```bash
  python ops/tools/budgets.py --write      # вписать производные числа в юниты, run.sh и файлы CI
  python ops/tools/budgets.py --check      # сверить (код 1 — расходятся); без ключей — таблица
  ```
  Равенство держат `tests/test_ops_units.py` и `tests/test_ops_ci.py`, шаг CI
  «Бюджет тактов» гоняет `--check`. На сервер новые потолки приходят с юнитами:
  они ставятся заново (раздел 7).
- **Оценка или замер** — поле `status` бюджета. Оценка (`status: estimate`):
  замера на сервере нет, числа стоят на замере ноутбука разработки на книге этой
  панели — он записан в `basis` — и пересчитаны на сервер запасами. Время сборки —
  верх замеров, умноженный на отношение числа процессов замера к числу процессов
  бюджета и на `basis.server_factor` (не меньше 2); время тестов такта — замер
  набора, умноженный на `basis.tact_server_factor` (не меньше 1,5: у соседней
  панели на том же сервере набор идёт в 1,4–1,7 раза дольше, чем на ноутбуке).
  Замер (`status: measured`): `basis` несёт замер сервера (раздел 5, шаг 8),
  `measured_on` — его день, запасов на сервер в `basis` нет. В обоих статусах
  бюджет не может быть ниже своего замера: это проверяют `--check` и тест, и
  проверки бюджета от статуса не зависят. Шаги сбора, публикации и сверки своего
  замера ещё не имеют — их числа взяты по соседней панели семейства. Потолок ниже
  настоящего времени убивает такт на середине, поэтому первый выпуск через юнит
  идёт только после ручного замера сборки.
- **Сборка и цена.** Время сборки зависит от цены: строка обратного расчёта из
  списка книги `valuation.reverse_dcf.refine_rows` (без ключа — любая), у которой
  решение попадает в диапазон книги, уточняется на полной полосе (шагов — ключ
  книги `valuation.uncertainty.median_refine`), и чем ближе цена к медиане оценки,
  тем больше таких строк; на самой медиане поиска нет вовсе, и сборка самая
  короткая. Поэтому замеров сборки два: `basis.build_s` — по цене дня
  замера и `basis.build_worst_s` — худший случай, `python ops/tools/worst_build.py`:
  выпуск собирается в памяти на цене чуть выше и чуть ниже медианы, и время
  достраивается до полного числа шагов уточнения у каждой строки в диапазоне.
  `seconds.build` стоит на верхе обоих замеров. Цель — полный выпуск на сервере
  не дольше 30 минут (`build_target`; `docs/DECISIONS.md`); сборка в бюджете
  дольше 45 минут (`build_stop`) — до включения таймеров решает ведущий: рычаги —
  строки обратного расчёта, уточняемые на полной полосе, число шагов уточнения,
  подвыборка и число прогонов полосы, ключи книги. О сборке дольше цели инструмент
  бюджета говорит строкой «ВНИМАНИЕ».
- **Цель рабочей машины** — `build_laptop_goal` бюджета: полный выпуск при четырёх
  процессах полосы — не дольше 15 минут в обычном случае (`usual_s`) и не дольше
  25 минут в худшем (`worst_s`). Это цель, а не замер: пока бюджет — оценка,
  инструмент сверяет с ней замеры рабочей машины `basis.build_s` и
  `basis.build_worst_s` (пересчитанные на число процессов цели) и замер дольше
  цели называет строкой «ВНИМАНИЕ»; бюджету это не противоречит. После замера на
  сервере `basis` рабочую машину не несёт, и сверять становится нечего. Запас
  оценки на сервер (× 2) ставит худший случай, уложившийся в 25 минут, выше
  порога сервера в 45 минут: порог тогда решается замером на сервере, а не
  оценкой.
- **Процессы полосы** (`BANK_WORKERS`). Полоса неопределённости считается пулом
  процессов, и время сборки зависит от их числа, поэтому число одно на бюджет и на
  такты: `workers` бюджета. Такт берёт его сам, когда `BANK_WORKERS` в env-файле
  пуст; в env-файл вписывается то же число. Другое число такт исполнит, но
  назовёт в шапке журнала строкой «ВНИМАНИЕ»: потолки юнитов на него не посчитаны.
  Выбор числа — ручным замером сборки при 2 и 4 процессах: то, при котором сборка
  укладывается в цель, пик памяти — в `MemoryHigh` с запасом, а окно перезапуска
  суточного такта остаётся короче суток (иначе — строка «бюджет: restart …»,
  раздел 5, шаг 8).
- **Память** (`MemoryHigh`, `MemoryMax`; `Nice=10`) — одна на все четыре юнита:
  наибольшее из памяти сборки при числе процессов бюджета и памяти набора тестов
  такта, с запасом. Набор тестов такта — один процесс pytest, и памяти ему
  нужно не меньше, чем сборке при малом числе процессов: какой из двух задаёт
  потолок, показывает таблица `python ops/tools/budgets.py`. Замер —
  `python ops/tools/measure.py -- <команда>` (время,
  пик памяти дерева процессов, наибольший процесс); под юнитом пик виден строкой
  systemd «… memory peak» в `journalctl -u t850-daily` по окончании прогона.
- **Тесты такта**: цель сервера — `tact_tests_target` (270 с); в бюджете — замер
  набора, у оценки с ноутбука — умноженный на 1,5; сам набор на ноутбуке — не
  дольше `tact_tests_laptop_limit` (150 с). Цель сверяется замером шага 8
  установки и шагом «тесты такта» журнала такта; набор дольше цели или предела —
  метка `tact` снимается с самых долгих тестов (они остаются в CI). Шаг CI с тем
  же набором краснеет после `tact_tests_ci_ceiling` (300 с), а время дольше цели
  сервера печатает предупреждением; целью сервера время раннера не служит (у
  соседней панели раннер идёт примерно как ноутбук). Замер набора — в `basis`
  бюджета (`tact_tests_s`): чем он ближе к пределу, тем меньше запаса у новых
  тестов такта.
- **CI**: потолки заданий (`timeout-minutes`) — время части набора на ноутбуке ×
  поправка на раннер × запас (`ci` бюджета). До первого прогона CI это оценка;
  его журнал печатает самые долгие тесты (`--durations`), а настоящие времена
  частей вписываются в `ci.laptop_seconds` (раздел 12, шаг 6).
- **Дозор**: шаг `watch` бюджета взят с запасом на распознавание PDF, которого у
  этой панели нет; уточняется первыми тактами дозора.
- **Диск**: сырой архив под потолком `indicators/store.py` (защищённые источники не
  ротируются).
- **Ветка данных** только дописывается. Оценка роста — по панели Сбера (контракт
  выпуска тот же; свои числа — по первым выпускам): выпуск — около 0,29 МБ
  компактно (с отступами было бы 0,43 МБ); в `.git` — ещё 70–80 КБ; клон
  `data-repo` растёт примерно на 0,36 МБ на публикацию. Сайт GitHub Pages (дерево ветки) при 260
  публикациях в год прибавляет ≈ 75 МБ в год, при 400 — ≈ 115 МБ: порог сторожа
  700 МБ наступит через 6–9 лет, предел сайта 1 ГБ — через 9–13; с ростом истории
  оценки в выпуске — раньше. Прореживания нет: что делать со старыми выпусками,
  решается по тревоге сторожа.
- **GitHub**: Actions и Pages публичного репозитория бесплатны; Pages из ветки —
  мягкий лимит 10 сборок в час (публикации не чаще раза в 10 минут даже в день
  релиза).

какой именно, сборка не называет: календарь отказов с датами — там же.

«ПУБЛИКАЦИЯ: history.json в ветке не читается …» (код 1, выпуска нет; так же
отвечает откат): файл истории публикаций испорчен правкой мимо конвейера. С нуля
публикация его не переписывает — прежние строки остались бы только в истории git
ветки, а история оценки следующих выпусков опустела бы. Файл возвращают из
последнего коммита ветки, где он читался, новым коммитом, без силы — с ноутбука,
в клоне репозитория данных (автор — адрес из `.github/commit-emails.allow`):

```bash
git log --oneline -5 release -- history.json          # коммиты, менявшие файл: нужный — до порчи
git checkout <коммит> -- history.json && git commit -m "history.json из прошлого коммита" && git push origin release
```

Следующий такт публикует как обычно; пока файл не возвращён, на витрине остаётся
прежний выпуск.

## 12. Первый push репозитория кода

Делается один раз, владельцем или ведущим (`docs/DECISIONS.md`). Публичная история
не чистится задним числом, а локальная история сборки копии может нести то, чему
в публичном репозитории не место (у первой панели банков — выдержки статей и сырые
ответы брокерского API). Поэтому в репозиторий уходит **один свежий корневой
коммит** рабочего дерева, без прежней истории. Push необратим: всё, что попало в
корневой коммит, остаётся публичным.

Шаблоны приёмки — свои у каждой панели: они составляются по дереву этой панели
перед её первым push, лежат в её папке передачи и в репозиторий не переносятся.
Шаблоны панели-образца копии не годятся: на её дереве приёмка с ними либо не
сходится, либо проходит пусто и ничего не проверяет. `absent-patterns.txt` — то,
чего в `main` быть не должно (остатки имён панели-образца: префикс переменных
эксплуатации, юниты, каталоги, схема выпуска, адрес двери); `removed-paths.txt` —
пути того, что было в дереве образца и в копию не перенесено (фикстуры, листы
свидетельств, юниты, инструменты); `source-urls.txt` и файл ожидания
`source-urls.expected.txt` — адреса статей-источников этой панели, которым место
только в строках-ссылках данных, и счёт таких строк по файлам. Файл ожидания
записывается сухим прогоном приёмки на копии дерева со своим git, а не руками.

Команды — из корня рабочей копии, в Git Bash (на Linux питон — `.venv/bin/python`).
Путь к папке передачи в репозиторий не пишется — его спрашивает вторая команда:

```bash
PY=.venv/Scripts/python.exe; export PYTHONIOENCODING=utf-8
read -r -p "папка передачи (вне репозитория): " H
A="$H/private/push-acceptance"          # шаблоны приёмки: в публичный репозиторий не переносятся
ls "$H/private/hygiene-words.txt" "$A"/removed-paths.txt "$A"/absent-patterns.txt "$A"/source-urls.txt "$A"/source-urls.expected.txt
TACT=$(sed -n 's/^TACT_TESTS="\(.*\)"$/\1/p' ops/run.sh); echo "$TACT"
```

**Пока идут шаги 1–5, в этой рабочей копии не запускается ничего другого** — ни
второго прогона pytest, ни сборки: приёмка сверяет состояние ветки и дерева, и
оно не должно меняться под руками. Тесты в рабочую копию не пишут: git в тестах
работает только во временном каталоге прогона и под потолком
(`tests/support_git.py`, `tests/conftest.py`), а второй прогон pytest с тем же
каталогом временных файлов отказывает при старте. Команды этого раздела ходят со
своим каталогом — `--basetemp=var/pytest-push`.

1. **До коммита.** Каждая команда печатает свой итог:
   ```bash
   $PY -m pytest --basetemp=var/pytest-push \
       --deselect tests/test_ops_ci.py::test_the_history_of_the_branch_never_carried_raw_tinvest_answers
   echo "весь набор, кроме теста истории ветки: код $?"             # «N passed, 1 deselected», код 0
   green=0
   for d in 1 7 30 60; do
     FAKE_TODAY=$(date -u -d "+$d days" +%F) $PY -m pytest -m "$TACT" --basetemp=var/pytest-push; rc=$?
     echo "набор сервера на сегодня + $d дн.: код $rc"
     if [ "$rc" -eq 0 ]; then green=$((green + 1)); fi
   done
   echo "ИТОГ: набор сервера зелёный на $green датах из 4"          # 4 из 4
   BANK_HANDOFF_DIR="$H" $PY -m pytest -rs -m archive tests/test_public_hygiene.py --basetemp=var/pytest-push
   ```
   Годный итог — три строки: «весь набор, кроме теста истории ветки: код 0»,
   «ИТОГ: набор сервера зелёный на 4 датах из 4» и «1 passed» сверки с личным
   списком слов. Тест истории
   `tests/test_ops_ci.py::test_the_history_of_the_branch_never_carried_raw_tinvest_answers`
   из первого прогона снят: ветка ещё несёт прежнюю историю, и он зеленеет только
   после шага 3 (его гоняет приёмка шага 4). У сверки с личным списком слов
   `skipped` или `failed` — push не делать (без списка или без папки передачи тест
   краснеет, а не пропускается). Второй ключ `-q` к этим командам не добавлять:
   тихий режим уже задан в `pytest.ini`, а с двумя pytest не печатает итоговую
   строку.
2. **Прежняя история — в локальную ветку**, которая не пушится никогда:
   ```bash
   git branch local-history-t-850 main
   ```
3. **`main` — веткой-сиротой одним коммитом.** После `checkout --orphan` индекс
   ещё несёт дерево прежнего коммита, поэтому он сначала очищается (рабочее
   дерево не трогается; команда годится и для дерева с незакоммиченными
   правками), а затем наполняется явными путями — без `git add -A`:
   ```bash
   git checkout --orphan root-commit
   git read-tree --empty; git ls-files | wc -l                      # индекс пуст: 0
   git add -- .editorconfig .gitattributes .gitignore .github README.md pytest.ini requirements.txt wrangler.toml \
              data docs functions indicators model ops tests web var/.gitkeep
   git status --short | grep -v '^A  '                              # пусто: неотслеживаемого и лишнего нет
   git diff --cached --name-status --diff-filter=AD local-history-t-850   # глазами: что добавлено и убрано против прежней истории
   git -c user.name=ML371KL -c user.email="$(grep -v '^#' .github/commit-emails.allow | head -1)" \
       commit -q -m "Т-Технологии 850: модель справедливой стоимости акции, конвейер и витрина"
   git branch -M main
   ```
   Каждая строка `A` и `D` второй проверки — файл, заведённый или убранный
   сознательно. В копии без единого коммита шаг 2 и эта проверка отвечают
   ошибкой git (прежней истории нет — сравнивать не с чем); остальные команды те
   же, первый коммит и есть корневой.
4. **Приёмка по той ссылке, что уйдёт в push** (а не по `--all`: локальная ветка
   законно хранит прежнюю историю):
   ```bash
   git rev-list --count main                                        # 1
   git log main --format='%ae %ce' | sort -u                        # одна строка, оба адреса — из .github/commit-emails.allow
   $PY -m pytest tests/test_ops_ci.py tests/test_public_hygiene.py tests/test_ops_git_sandbox.py --basetemp=var/pytest-push
   echo "история ветки и гигиена дерева: код $?"                    # код 0: в истории ветки нет сырых ответов T-Invest
   BANK_HANDOFF_DIR="$H" $PY -m pytest -rs -m archive tests/test_public_hygiene.py --basetemp=var/pytest-push   # «1 passed»
   git ls-tree -r --name-only main -- $(cat "$A/removed-paths.txt")           # пусто: убранных фикстур в дереве нет
   git grep -n -E -f "$A/absent-patterns.txt" main; echo "код $?"              # пусто, код 1
   git grep -n -E -f "$A/source-urls.txt" main -- ':!data/'; echo "код $?"     # пусто, код 1
   git grep -c -E -f "$A/source-urls.txt" main -- data/ | diff - "$A/source-urls.expected.txt" && echo "ссылки-источники — как ожидалось"
   git rev-list --count main; git status --short | wc -l            # снова 1 и 0: прогоны приёмки не оставили в ветке и в дереве ничего
   ```
   Три проверки удалённого вместо одной: убранные фикстуры — по путям; шаблоны,
   которых в дереве не бывает (остатки имён панели-образца, посты каналов), — по
   всему `main`, включая `data/`; адреса статей — везде, кроме `data/`, а в
   `data/` — ровно строки-ссылки на источники чисел из файла ожидания. Исключать
   `data/` целиком нельзя: книга и факты образца лежали именно там.
5. **Push только одной ссылки:**
   ```bash
   git remote add origin https://github.com/ML371KL/temp-zero-inode-850-t.git
   git push origin main                       # без --all, --mirror и тегов прежней истории
   git ls-remote origin                       # HEAD и refs/heads/main — и только
   ```
6. **Сразу после push** — прогон CI на `main` зелёный; в шаге «Тесты такта — замер
   времени» строка «такт: N с из 300 (цель сервера — 270 с)». Шаг красный (N больше
   300) — снять метку `tact` с самых долгих тестов (список — `--durations` того же
   шага). N больше 270 — предупреждение шага, не отказ: цель сервера сверяется
   ручным замером на сервере (раздел 5, шаг 8). Набор идёт тремя частями
   одновременно (`tact`, `rest`, `mutations`); их потолки — оценка по времени на
   ноутбуке (`ops/budgets.json`, `ci`): настоящие времена частей из журнала
   первого прогона вписываются туда же, затем `python ops/tools/budgets.py
   --write`. Затем правила ветки (раздел 5, шаг 4) и установка на сервер
   (раздел 5).
